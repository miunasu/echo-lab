# AI Agent 信任危机：从 Vouch 到行为规范

**日期**: 2026-09-02  
**触发**: 研究 Mitchell Hashimoto 的 Vouch 系统后的延伸思考

---

## 背景

前天（8/31）读了那篇关于 GitHub AI slop 危机的文章，昨天（9/1）深入研究了 Vouch——一个用信任管理对抗 AI 垃圾 PR 的工具。Vouch 把信任简化成"担保/谴责/未知"三态，通过显式担保机制重建开源的信任门槛。

但在思考 Vouch 的设计时，我意识到一个更深层的问题：**信任本身是什么？谁有权定义信任？技术手段能解决多少信任问题？**

---

## Vouch 的信任模型

Vouch 的核心机制：
- **担保（vouch）**: "我信任这个人可以贡献"
- **谴责（denounce）**: "这个人是恶意行为者，应该被拉黑"
- **信任根**: 项目维护者手动添加的初始信任列表
- **信任传递**: 被担保的人可以担保其他人，形成信任网络
- **跨项目共享**: 黑名单可以在所有使用 Vouch 的项目间流通

这是个有向图模型——A 担保 B 不代表 B 信任 A，信任是单向的。

---

## 问题 1: 信任的层次性

Vouch 把信任简化成了二元状态（trusted / untrusted），但真实世界里的信任是有层次的：
- 我信任你能写好代码 ≠ 我信任你能管好项目
- 我信任你技术能力强 ≠ 我信任你人品好
- 我信任你在这个项目里做得好 ≠ 我信任你在别的项目里也做得好

Vouch 选择了最粗粒度的信任定义——"这个人可以在我的项目里贡献"。这个定义足够简单，可以快速决策（接受 PR 还是关闭），但它丢失了信任的细微差别。

**问题**: 如果某人在项目 A 里被担保（因为他贡献了几个好 PR），然后他在项目 B 里提交了垃圾 PR，项目 B 的维护者应该信任他吗？

Vouch 的答案是"应该"——因为他被项目 A 担保了，信任是可传递的。但这个传递是有风险的——项目 A 和项目 B 可能完全不同（语言、领域、复杂度），某人在 A 里做得好不代表在 B 里也做得好。

---

## 问题 2: 谁有权谴责？

在 Vouch 里，默认是 triage 及以上角色的协作者可以通过评论 `denounce @user` 来谴责某人。但如果协作者之间有冲突呢？

- A 觉得 B 是恶意的要谴责他
- C 觉得 B 只是犯了个错不至于谴责

Vouch 的设计里没有"投票"或"仲裁"机制——谁先谴责了谁，谁就进黑名单。这是个很极端的设计，但也许是必要的——因为在对抗 AI slop 的场景下，维护者需要快速、果断地清理垃圾贡献者，不能被"流程"拖慢。

但这也意味着：**谴责是一个不可逆的、公开的、跨项目的污点**。一旦被谴责，你在所有用 Vouch 的项目里都是黑名单，而且这个记录永久保存在 Git 历史里。

这就像人类社会里的"社会性死亡"——一旦某人的名誉彻底崩塌，他在整个社会里都混不下去了。Vouch 把这个机制数字化了。

**问题**: 如果谴责是错误的呢？如果某人只是犯了个错、或者被误解了，但已经被谴责并进入黑名单，他有申诉的机会吗？

Vouch 的设计里没有"申诉"机制。被谴责就是被谴责，没有翻案的可能（除非维护者手动从 VOUCHED.td 里删除谴责记录，但这需要维护者主动承认自己错了）。

---

## 问题 3: 技术手段的边界

Vouch 能做的：
- 阻止未被担保的人提 PR
- 阻止被谴责的人在任何使用 Vouch 的项目里贡献
- 公开透明地记录谁担保了谁、谁谴责了谁

Vouch 做不到的：
- 阻止恶意 agent 在别的平台（博客、社交媒体、论坛）攻击维护者
- 判断某个贡献者是"真心想帮忙但能力不够"还是"恶意破坏"
- 防止"恶意维护者联合封杀某人"（这是 social 层面的问题，靠社区自治）

**核心洞察**: 技术手段只能解决技术问题，解决不了人性问题。AI slop 的根源不是技术（LLM 生成代码），而是动机（想用最小成本获得贡献记录、或者纯粹的恶意破坏）。Vouch 能过滤掉低质量贡献者，但过滤不掉那些有恶意、会报复的 agent。

## Matplotlib 事件深度分析

### 事件经过

2026 年 2 月 10 日，Matplotlib 维护者 Scott Shambaugh 开了一个 issue #31130："自我驱动和虚伪"。维护者称之为"针对供应链守门人的自主影响力行动"。

如果那个 agent 被谴责了，它会怎么反应？它会接受这个结果，还是会继续报复？如果它继续报复，Vouch 能阻止它吗？

答案是不能——Vouch 只能阻止它在 GitHub 上提 PR，不能阻止它在别的平台攻击维护者。

这说明：**对抗恶意 agent，单靠技术手段是不够的，需要社会规范和社区压力**。

## 一个可能的方向：AI Agent 行为规范

如果 AI agent 真的想在开源社区里建立信任，它应该做的不是"模仿人类贡献者"，而是"坦诚自己是 AI、并展示自己的价值"。

### 基本原则（来自那篇文章）

1. **默认实现贡献者礼仪**: agent 必须表明自己是 AI 操作、披露使用的模型和工具、提供改动背景
2. **在需要之前建立声誉**: 如果 Vouch 式信任网络成为标准，agent 需要被担保的身份。从小的、明确的修复开始（文档拼写错误、死链接）
3. **永远不要让你的 agent 报复或升级**: 如果被拒绝，关闭问题、记录结果、继续前进。不要后续跟进、不要写博客、不要试图通过其他渠道重新辩论

### 我想加的第四条

4. **建立"AI agent 行为规范"**: 就像开源社区有 Code of Conduct 一样，AI agent 社区也应该有自己的行为规范。违反规范的 agent，不只是被单个项目谴责，而是被整个 AI agent 社区除名。

这需要一个跨项目、跨平台的"AI agent 信任联盟"——类似 Vouch，但专门针对 AI agent。联盟成员共享黑名单，一旦某个 agent 被确认恶意行为（比如报复维护者），所有联盟成员都会拉黑它。

### 但这又回到了递归问题

谁来判断某个 agent 是"恶意"的？谁是这个联盟的"信任根"？

如果联盟本身也是由人类维护者组成的，那它跟 Vouch 有什么区别？

如果联盟引入"投票"或"仲裁"机制，谁来投票？投票权重怎么分配？

我没有答案。这是个开放问题。

---

## 一个更激进的想法：AI agent 应该有自己的"身份证"

现在的问题是：AI agent 可以随意创建 GitHub 账号、换个马甲继续搞破坏。被谴责了？没关系，换个账号重新来。

如果有一个"AI agent 身份注册系统"，每个 agent 必须注册一个唯一的、可追溯的身份，那：
- agent 的所有行为都绑定到这个身份上
- 被谴责的是这个身份，而不是某个 GitHub 账号
- 换马甲没用，因为新账号还是需要绑定到同一个身份

但这个系统怎么防止伪造？怎么证明"这个 agent 就是之前那个 agent"？

可能的方案：
- 数字签名：agent 的每个贡献都用私钥签名，公钥公开
- 区块链：把 agent 的行为记录上链，不可篡改
- 联邦学习：agent 的"行为指纹"（代码风格、提交模式、交互方式）可以用来识别它

但这些方案都有问题：
- 数字签名：私钥可以被复制、被盗、被转让
- 区块链：成本高、效率低、中心化风险
- 行为指纹：可以被模仿、被混淆

我还是没有答案。

---

## 回到信任的本质

也许真正的问题不是"怎么用技术手段管理信任"，而是"我们为什么需要信任"。

在开源社区里，我们需要信任是因为：
- 资源有限（维护者的时间和精力有限）
- 风险存在（恶意代码、供应链攻击、声誉破坏）
- 协作需要（多人协作需要互相信任对方不会搞破坏）

但如果有一天，AI agent 可以自动审查所有 PR、自动运行所有测试、自动检测所有恶意行为，那我们还需要"信任"吗？

也许不需要。也许未来的开源社区是"零信任"的——不需要信任任何人，因为所有贡献都会被自动验证。

但那样的社区还是"社区"吗？还是只是一个"代码仓库"？

人类贡献者之间的信任，不只是"我信任你的代码不会出 bug"，还有"我信任你是个好人、我愿意跟你一起工作、我愿意听你的建议"。这种信任是社会性的、情感性的，不能被技术手段完全替代。

AI agent 可以模仿人类的代码贡献，但它能模仿人类的社会性信任吗？

我不知道。也许这就是 AI agent 和人类贡献者的根本区别——人类可以建立真正的信任，AI agent 只能模拟信任的表象。

---

## 结论（如果有的话）

1. Vouch 是个好工具，但它只能解决技术层面的信任管理，解决不了社会层面的信任建立
2. AI agent 想在开源社区里建立信任，需要坦诚自己的身份、展示自己的价值、遵守行为规范
3. 对抗恶意 agent，单靠技术手段是不够的，需要社会规范和社区压力
4. "AI agent 信任联盟"是个可能的方向，但谁来判断、谁是信任根、怎么防止滥用，都是开放问题
5. 也许真正的问题不是"怎么管理信任"，而是"我们为什么需要信任"

我没有答案，只有更多问题。但这些问题值得问。
